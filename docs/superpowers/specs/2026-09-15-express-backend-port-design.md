# InvoicePilot — Express Backend Port

**Date:** 2026-09-15
**Status:** approved, awaiting implementation plan
**Supersedes:** `docs/superpowers/specs/2026-09-15-node-backend-port-design.md` in full (see §10)

---

## 1. Context

The backend is a FastAPI service in `backend/`: 61 Python files, 14 route
modules, 55 endpoints. Five of those endpoints do real work — signup, login,
refresh, logout and switch-workspace. The other fifty are a function signature,
an RBAC guard and a `501`.

An earlier spec on this same date planned the same move to Node and rejected
Express, folding the API into Next Route Handlers on one Vercel deployment.
Its phase P1 landed: a TypeScript Drizzle schema, two SQL migration files, a
migration runner, a database client, and five Vitest suites — seven commits,
1,122 lines under `src/server/`.

Express is now a hard requirement. That reverses the earlier rejection and,
with it, the single-deployment topology that depended on it. The frontend stays
TypeScript on Next 16. The backend becomes JavaScript on Express, deployed
separately, structured as MVC.

**What survives from P1:** the SQL. `drizzle/0000_schema.sql` and
`drizzle/0001_derivation_views.sql` are language-neutral and move byte for
byte. The migration runner is plain logic wearing type annotations, and moves
with them stripped.

**What P1 loses:** `src/server/models/schema.ts` (414 lines, generated by
introspection) and the five Vitest suites. Drizzle exists to infer TypeScript
types; JavaScript cannot use them, so the dependency would be paid for nothing.
The suites are rewritten against `node:test` and raw SQL.

## 2. Decisions

| # | Decision | Consequence |
|---|---|---|
| 1 | Express 5, JavaScript, ESM, in `backend/` | The Python service is replaced in place. The frontend does not move. |
| 2 | Deployed to Render's free tier as a long-lived web service | Not serverless. A real process with a real connection pool. |
| 3 | The frontend stays on Vercel, TypeScript, unchanged | `API_BASE_URL` already exists and already points at a remote backend. Zero frontend code changes. |
| 4 | The browser never calls the backend | Only the Next server does, with a bearer token. No CORS middleware, no CSRF surface. |
| 5 | postgres.js with hand-written SQL, no ORM | The derivation views already do the derivation. Drizzle's value was type inference, which JavaScript discards. |
| 6 | MVC: `routes/`, `controllers/`, `models/`, one file per domain in each | 14 domains, 42 files. Chosen explicitly over the leaner concern-based split. |
| 7 | `services/` only where real rules exist | An empty pass-through layer per domain is a file to read at 3am for nothing. Today that means `services/auth.js` and nothing else. |
| 8 | All 55 endpoints ship, 50 of them returning `501` | Endpoint parity with the Python service from the day it is deleted. Stub controllers are one line each. |
| 9 | `node:test`, not Vitest | Built in, no config, runs `.js` directly. Vitest existed to resolve `@/` and to run TypeScript; the backend has neither problem. |
| 10 | Argon2 parameters drop from 64 MB to the `@node-rs/argon2` defaults | Render's free tier has 512 MB of RAM. See §5. |

## 4. Layout

```
backend/
├── package.json              type: module, own dependencies, own lockfile
├── src/
│   ├── server.js             reads config, migrates, listens
│   ├── app.js                express app, routers, error handler last
│   ├── config.js             environment read once, fail fast
│   ├── db/
│   │   ├── index.js          postgres.js client, bigint policy
│   │   ├── migrate.js        applies sql/*.sql not yet run
│   │   └── seed.js           demo workspace, fixed RNG seed
│   ├── sql/
│   │   ├── 0000_schema.sql
│   │   └── 0001_derivation_views.sql
│   ├── middleware/
│   │   ├── authenticate.js   bearer token to Principal
│   │   ├── require.js        one named permission
│   │   └── errors.js         DomainError to HTTP, unhandled to 500
│   ├── routes/               14 files
│   ├── controllers/          14 files
│   ├── models/               14 files
│   ├── services/
│   │   └── auth.js
│   └── lib/
│       └── security.js       argon2, JWT, refresh tokens, ROLE_PERMISSIONS
└── tests/
```

MVC maps as: `routes/` wires paths to guards and controllers, `controllers/`
handle HTTP — validate, delegate, shape — `models/` own data access, and the
view is the React already deployed on Vercel. Business rules live in
`services/` when a use case spans more than one statement.

A stub `models/<domain>.js` is not empty. It carries a header comment naming
the tables and views that domain will own, so the directory reads as a map of
the schema rather than a directory of blanks.

## 5. Auth and security

The only subsystem with real logic, and the only part of this port carrying
real risk. The Python behaviour is reproduced exactly.

| Concern | Python | JavaScript | Why |
|---|---|---|---|
| Password hash | `argon2-cffi` | `@node-rs/argon2` | Prebuilt binaries; no node-gyp in Render's build |
| Access token | `pyjwt`, HS256 | `jose`, HS256 | Zero dependencies, native ESM |
| Refresh token | `secrets.token_urlsafe(32)` | `node:crypto` `randomBytes(32).toString("base64url")` | Standard library |
| Refresh digest | `hashlib.sha256` | `node:crypto` `createHash("sha256")` | Standard library |
| Permissions | `dict[Role, frozenset[str]]` | `Object.freeze` over `Set` | Data, not branching |
| Principal | frozen dataclass | plain object with `can()` | Identity, not a query parameter |

Claims are unchanged: `sub`, `ws`, `role`, `iat`, `exp`, thirty-minute expiry.
Refresh tokens stay opaque and stay SHA-256, for the reason recorded at
`security.py:117-127` — they are looked up on the hot path of every refresh,
and a 300 ms key derivation there is a self-inflicted denial of service. The
token is 256 bits of urandom, so there is no dictionary to attack.

`ROLE_PERMISSIONS` ports verbatim, including one wart: `billing.py` guards with
`billing:write`, which no role grants, so only `owner` reaches it through `*`.
A hosting change that quietly widens a permission is a defect. Fixing it is a
separate decision.

`Principal.workspace_id` comes from the token. Every model function takes it as
its first argument and builds its statement through one shared scoping helper,
so a caller cannot widen their own scope by editing a URL or a body. That is
`WorkspaceRepository._query()` carried across.

### Argon2 parameters

`argon2-cffi` defaults to 64 MB of memory per hash. Render's free tier has
512 MB of RAM for the whole process. `@node-rs/argon2` defaults to 19 MB, time
cost 2, Argon2id — the current OWASP recommendation. The defaults are taken as
they come.

No hashes exist in any deployed database, so nothing needs to verify against
the old parameters. Argon2 encodes its parameters in the hash string, so this
would be a compatible change even if hashes did exist.

### Why the backend does not read cookies

The browser holds `ip_at` and `ip_rt` as httpOnly cookies. A Server Action
reads the access token and sends it as a bearer token. The backend accepts
`Authorization: Bearer` and nothing else, which is why a cross-site request
cannot drive it: the attacker's page cannot read the cookie, and the API does
not accept one.

Separate origins preserve this by construction. `readAccessToken()` stays in
the Server Action layer, exactly where it is now.

## 6. Data layer

**Client.** postgres.js against Neon's pooled endpoint, `prepare: false`
because PgBouncer in transaction mode rejects prepared statements. `max: 5` —
Render runs a long-lived process, so it should hold a small pool. This reverses
the `max: 1` the superseded spec chose for Vercel functions; that constraint
left with the host.

**Money.** `amount_cents`, `paid_cents` and `balance_cents` are `bigint`.
postgres.js returns `int8` as a string to avoid silent precision loss, so a
single `types.bigint` override in `db/index.js` parses them to numbers once,
asserting the value is below `Number.MAX_SAFE_INTEGER`. Deciding this per query
is how one screen ends up formatting `"120000"` as a string.

**Migrations.** `backend/src/db/migrate.js` applies every `src/sql/*.sql` file
not recorded in the `_migrations` table, in filename order, each in its own
transaction. It runs at boot, before `listen()`. Render's free tier has no
pre-deploy hook, the operation is idempotent, and a free plan runs one
instance, so nothing races.

**Derivation views.** `invoice_state`, `customer_stats` and `collection_queue`
keep defining every derived value. Models are thin SQL over them. The risk rule
is not re-implemented in JavaScript.

**Transactions.** Payment application and any other multi-statement write run
inside `sql.begin()`. The ledger invariants are transactional invariants; they
do not survive being split into separate statements.

**Validation.** Zod replaces the Pydantic schemas. It is runtime validation and
works unchanged in JavaScript.

## 7. Seeder

`app/seeds/demo.py` and `app/seeds/rng.py` (467 lines together) port to
`backend/src/db/seed.js` with the seed value fixed, so reseeds are identical
and screenshots agree with bug reports.

`src/lib/data/seed.ts` (715 lines) stays on Vercel. It builds the same shape of
data as in-memory fixtures for the six parked preview screens, and the
superseded spec intended to collapse the two. That is no longer possible: they
now live in different services and different languages. The duplication is
accepted with an end date — `src/lib/data/` is deleted when phase 6 unparks the
last preview screen.

## 8. Frontend wiring

No frontend file changes.

`src/lib/api/client.ts:16` already reads `process.env.API_BASE_URL`.
`src/proxy.ts:110` already posts to `${API_BASE_URL}/api/auth/refresh`. Both
were written against a remote FastAPI service, and a remote Express service at
the same paths is the same contract. Deployment sets `API_BASE_URL` to the
Render URL.

Refresh rotation stays in `proxy.ts`, where it is today. The superseded spec
moved it out because Vercel service bindings do not resolve in middleware;
there is no binding here, so the constraint never arises.

## 9. Deployment

| | Render | Vercel |
|---|---|---|
| Service | Web service, free plan | Next 16, hobby |
| Root | `backend` | `.` |
| Build | `npm ci` | `next build` |
| Start | `node src/server.js` | — |
| Env | `DATABASE_URL`, `SECRET_KEY`, `ADMIN_TOKEN`, `DEMO_WORKSPACE_ID` | `API_BASE_URL` |

One Neon free database serves both environments through `DATABASE_URL`.

`vercel.json` reduces to its cron entry:

```json
{
  "crons": [{ "path": "/api/cron/reseed", "schedule": "0 4 * * *" }]
}
```

Render's free plan has no cron jobs, so reseeding is a `POST /api/admin/reseed`
guarded by `ADMIN_TOKEN`, and Vercel's single daily hobby cron hits a Next route
that forwards to it.

**Free-tier budget.** Render's free plan allows 750 instance hours per month and
suspends a service after 15 minutes of inactivity, costing roughly 50 seconds on
the next request. Running continuously costs 730 hours, which fits inside the
allowance, so an external five-minute ping keeps the service awake within
budget. Neon's free plan suspends after five minutes idle regardless, so the
first query after a quiet period still pays a wake-up.

## 10. What this supersedes

`2026-09-15-node-backend-port-design.md` is superseded in full. Its decisions
1, 2, 3, 4, 6 and 8 are reversed by the move to a separate Express service in
JavaScript. Its decision 5 — port only working code — is reversed by decision 8
here, which ships all 55 endpoints for parity. Its decision 7 survives in
changed form: a backend test framework is still required, but it is `node:test`
in `backend/`, not Vitest at the root.

From `2026-09-11-free-tier-deployment-and-phases-3-6-design.md`, the two-service
topology of decision 1 is restored, this time as Vercel plus Render rather than
two Vercel services. Decision 2 — the backend gets no public rewrite — is lost;
see §12. Decision 3's service binding is replaced by a plain environment
variable, and decision 4 is moot, since rotation stays in `proxy.ts`.

**Survives unchanged:** decision 5 (six screens stay banner-parked), decision 6
(one-click demo login, seated as admin), decision 7 (daily cron reseed),
decision 8 (email is an outbox with no provider), decision 9 (deploy the working
spine before building phases 3–6), and the acceptance criteria of phases 3
through 6.

The P1 plan, `2026-09-15-node-backend-port-p1-schema-and-views.md`, is complete
and merged. Its SQL output is what this port carries across; its TypeScript
output is deleted by P1 of §13 below.

## 11. Verification

**Harness.** Ported from `src/server/test/database.ts`: `assertTestDatabase`,
which refuses any database whose name does not contain `test`; `withRollback`,
which runs each test in a transaction that is always rolled back;
`expectConstraintViolation`; and the row factories. Files run sequentially
against one migrated database.

**Suites, in porting order**

| Suite | Ported from | Covers |
|---|---|---|
| views | `src/server/test/views-*.test.ts` | `invoice_state`, `customer_stats`, `collection_queue` |
| schema | `src/server/test/schema.test.ts` | constraints reject bad rows |
| security | `tests/test_security.py` | hashing and token round trips |
| permissions | `tests/test_permissions.py` | the permission matrix, row by row |
| auth service | `tests/test_auth_service.py` | rotation, and a reused token revoking its chain |
| tenancy | new | workspace A cannot read, update or delete a row in workspace B |
| ledger | `tests/test_ledger_invariants.py` | deferred to P3 with the seeder it depends on |

**CI.** One workflow, two jobs. `backend` runs `npm ci` and `node --test`
against a `postgres:16` service. `frontend` runs `tsc --noEmit` and
`npm run build`, and needs no database once the API is remote. The Python job is
removed.

**Manual.** After a deploy, log in as the demo user on the Vercel URL and load
the dashboard.

## 12. Risks and known constraints

- **The API becomes publicly routable.** The free-tier spec gave FastAPI no
  rewrite, so it could not be reached from the internet. A Render web service
  has a public hostname. The remaining defences are the ones that were always
  doing the real work — bearer authentication on every request, RBAC per route,
  workspace scoping in every model function — but defence in depth is genuinely
  reduced. Decision 4 in §2 keeps the cross-site property that the private
  service was also providing.
- **Auth is the only tested subsystem in the repository, and this rewrites it.**
  Mitigated by porting `test_security`, `test_auth_service` and
  `test_permissions` before the implementation, not after.
- **JavaScript loses the type contract between backend and frontend.** The
  frontend keeps Zod parsing at the boundary in `client.ts`, so a renamed field
  fails loudly at the parse instead of silently inside a formatter. That check
  is now the only thing standing where inferred types would have stood.
- **Two cold starts compound.** Render suspends at 15 minutes idle, Neon at 5.
  A first request after a quiet period can wait for both.
- **Fifty `501` endpoints are fifty endpoints' worth of surface that nothing
  tests.** Their only assertion is that the status and the detail string match
  the Python service they replace.
- **`node_modules/` is not installed at the repository root.** The Next 16
  guides under `node_modules/next/dist/docs/` cannot be read until
  `npm install` runs, and `AGENTS.md` requires them before any Next file is
  touched. This port changes no Next source file, but P3 edits `vercel.json`
  and the CI workflow.

## 14. Out of scope

Unchanged: the automations engine, third-party integrations, model-backed AI,
billing, API keys, webhooks, rate limiting, and the notification centre. Those
screens keep their preview banner until their sub-projects land.

Also out of scope: any change to the schema, the permission model, the session
design, or the product surface. This port changes the host, the language and
the framework. Anything else it appears to change is a defect.
